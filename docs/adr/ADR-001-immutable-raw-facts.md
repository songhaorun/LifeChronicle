# ADR-001：原始事实不可变

## 状态

Accepted。该决策随阶段 0 基线采纳生效；它不表示相关存储和删除工作流已经实现。

## 上下文

LifeChronicle 接收来自多设备、多 Provider 和外部导入的长期个人事实。来源可能迟到、
重复、修订或要求删除。如果原始行被处理器就地修改，就无法证明设备最初提交了什么，
也无法确定性回放新算法、解释统计差异或审计删除范围。

不可变不等于无限期保留。用户删除、法定义务和保留策略仍必须能够物理清除数据，但
清除只能由可审计工作流执行，不能由普通处理器以“修正”为名覆盖历史。

## 决策

- Agent 或外部来源提交的 Event、Series、文件和控制记录在接收后只追加保存。
- 修正使用 `Correction` 和独立 replacement Event；逻辑删除使用 `Tombstone`；
  标注使用 `Annotation`。这些记录必须引用稳定 ID，不得覆盖被引用事实。
- Iceberg Bronze 保存提交内容、来源、业务时间、Schema 版本和内容摘要；派生层只写
  新版本或新 revision，不回写 Bronze。
- ClickHouse、Silver/Gold、缓存和公开快照都是可重建或可撤销投影，不得成为原始
  事实的唯一副本。
- 物理删除只由版本化删除/保留 Workflow 按已批准范围执行，并记录计划、进度、
  失败、备份到期时间和审计证据。

## 备选方案

1. **按主键更新当前行。** 实现简单，但会丢失提交证据并使回放依赖更新顺序，拒绝。
2. **只保留数据库审计日志。** 审计日志通常不含完整领域语义且生命周期不同，不能
   代替原始档案，拒绝。
3. **永不物理删除。** 与用户删除和保留要求冲突，拒绝。

## 后果

正面后果：

- 可从固定输入快照重放并比较处理器版本；
- 来源、修正和删除链可审计；
- 热库或派生表损坏后可从原始档案重建。

负面后果：

- 修正查询必须解析引用和 revision，模型更复杂；
- 存储量增加，需要明确分层保留、compaction 和删除工作流；
- “已删除”必须区分逻辑不可见、在线存储清除和备份到期清除。

安全与隐私影响：原始层的权限必须最小化，日志和 Trace 不得复制 Payload；删除失败
必须失败可见，不能伪装为完成。

## 迁移

1. 盘点所有会就地更新事实的来源和表；
2. 冻结新的覆盖式写入，导出带来源和摘要的迁移快照；
3. 为现有当前值生成初始原始事实，为可证明的历史变化生成修正记录；
4. 让 Consumer 双读旧模型和新 append-only 模型并核对 ID、数量和业务不变量；
5. 切换读取后保留旧库只读直至验证、备份和回滚窗口结束。

## 回滚

迁移失败时停止新模型写入并把读取切回迁移前只读快照。已经写入的新原始事实不得
删除或改写；修复后从固定 offset/snapshot 重新派生。若错误数据必须清除，只能走
删除 Workflow。

## 测试

- `ES-C008`：同 ID 同内容为 Duplicate，同 ID 异内容为 Conflict；
- `ES-C014`：固定输入重复回放结果一致；
- `ES-C017`：五语言生成相同 Item 内容身份，覆盖字段或可信用户变化会改变摘要；
- `M3-05/M3-06`：从 Event/Batch 追踪到 Kafka offset、Iceberg snapshot 和文件；
- `M5-02/M5-04/M5-06`：版本化回放、删除 dry-run、故障恢复和备份到期语义；
- `ARC-008/ARC-010/ARC-012`：原始追踪、派生确定性和全存储删除证据。

## 退出条件

- Correction、Tombstone、Annotation 和稳定引用已进入统一契约；
- Bronze Sink 的崩溃恢复证明不覆盖、不漏写原始事实；
- 至少一个处理器能从固定 snapshot 重建相同逻辑结果；
- 删除测试能区分逻辑不可见、各在线存储清除和备份到期，并对部分失败报警；
- 任一普通业务服务均无直接覆盖 Bronze 对象或表记录的权限。
